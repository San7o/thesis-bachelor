\section{Event Sources}

The previous section explained various frameworks for supporting events traces
and making them available to the user. This section discusses some types of
events, focusing on their implementation and interaction with said frameworks.
Example pseudo-code and extracts from the Linux kernel codebase will be
included.

A distinction is made between \textit{static} events and \textit{dynamic}
events. Static events are placed by kernel developers in pre-determined
locations and statically compiled in the kernel. In contrast, dynamic events are
registered during runtime and can be registered in non-predetermined locations.

\subsection{Static Events}

\subsubsection*{Tracepoints}

A \textit{tracepoint} provides a way to call a function when the tracepoint is
executed, which is referred to as a "callback". Tracepoints are placed all over
the kernel alongside regular code and can be either set as "on", meaning a
callback is connected to it, or "off" meaning no hook is present. The callback
can accept custom parameters for tracing purposes. The usage of tracepoints is
conceptually simple, which will be explained with several examples.

Consider the following code:

\begin{Verbatim}[numbers=left, numbersep=5pt, frame=single]
void foo(void) {
  int x = bar();
  // ...

  trace_foo(x); /* Tracepoint placed here */

  // ...
  return baz(x);
}
\end{Verbatim}

Here the function \verb|trace_foo()| is executed somewhere in the function
\verb|foo| with the variable \verb|x| passed as an argument. \verb|trace_foo()|
belongs to a particular tracepoint, along side with other functions that are
generated by the tracpoint API when a tracepoint is defined. If the tracepoint
is currently active, this function will jump to callback function which can use
the \verb|x| variable for tracing purposes, for example to write it to the
ftrace or the perf ring buffer. This callback is specified when registering the
tracepoint.

The key types used by the tracepoint API are \verb|struct tracpoint|,
\verb|struct tracepoint_func| and \verb|struct tracepoint_ext| which are
reported below from the file
\textit{\$LINUX/include/linux/tracepoint-defs.h:26}, where \verb|\$LINUX|
represents the root of the kernel's source code:

\begin{Verbatim}[numbers=left, numbersep=5pt, frame=single]
struct tracepoint_func {
  void *func;
  void *data;
  int prio;
};

struct tracepoint_ext {
  int (*regfunc)(void);
  void (*unregfunc)(void);
  /* Flags. */
  unsigned int faultable:1;
};

struct tracepoint {
  const char *name;    /* Tracepoint name */
  struct static_key_false key;
  struct static_call_key *static_call_key;
  void *static_call_tramp;
  void *iterator;
  void *probestub;
  struct tracepoint_func __rcu *funcs;
  struct tracepoint_ext *ext;
};
\end{Verbatim}

The most relevant members of \verb|struct tracepoint| are its "name", which is
used by the user to identify a particular tracepoint, and the "funcs" member
used to specify one or more functions to be called when the tracepoint is
executed (which are of type \verb|struct tracepoint_func|). The "ext" (extended)
member contains optional functions to be called when registering or
unregistering the tracepoint. Additionally, the static-key and static-call
related fields are performance optimizations which will be briefly explained
later in this section.

To create a tracepoint, the macro \verb|DECLARE_TRACE| should be used. This
macro takes three arguments: the name of the tracepoint, the prototype of the
function that should be called when the tracepoint is executed, and the name of
the arguments what should be passed to that function (relevant to the specific
scope where the tracepoint is placed).

For example, consider the following macro statement:

\begin{verbatim}
DECLARE_TRACE(foo_tp,
  TP_PROTO(bool is_bar),
  TP_ARGS(bar));
\end{verbatim}

This declares a tracepoint called \verb|foo_tp| which calls a function that
looks like \verb|foo_function(bool is_bar)| which it will be called with the
\verb|bar| argument, like \verb|foo_function(bar)|.

Consider now a real example from \textit{\$LINUX/include/trace/events/sched.h}:

\begin{Verbatim}[numbers=left, numbersep=5pt, frame=single]
#undef TRACE_SYSTEM
#define TRACE_SYSTEM sched

#if !defined(_TRACE_SCHED_H) || defined(TRACE_HEADER_MULTI_READ)
#define _TRACE_SCHED_H

#include <linux/tracepoint.h>

DECLARE_TRACE(sched_entry,
  TP_PROTO(bool preempt),
  TP_ARGS(preempt));

#endif /* _TRACE_SCHED_H */

/* This part must be outside protection */
#include <trace/define_trace.h>
\end{Verbatim}

In the first line, the \verb|TRACE_SYSTEM| symbol specifies the subdirectory of
tracefs where this tracepoint will be registered for access to the user. The
code follows by including the file \textit{\$LINUX/tracepoint.h} which contains the
\verb|DECLARE_TRACE| macro definition, and proceeds to declare the
\verb|sched_entry| tracepoint. It finally includes \textit{trace/define\_trace.h}
which defines the various functions for the tracepoint and static storage, such
as functions for registration, de-registration, calling the callback, and a
function to check if the tracepoint is active, among others. The generated
function names would be, respectively: \verb|register_trace_sched_entry()|,
\verb|unregister_trace_sched_entry()|, \verb|trace_sched_entry()|,
\verb|trace_sched_entry_enabled()|. The registration function accepts the
callback function to be called when the tracepoint is executed.

It should be noted that the \verb|define_trace.h| header needs to be placed
outside any inclusion guards so that it will be always included by the
preprocessor. This is used for a trick with the preprocessor where the
\verb|define_trace.h| header includes the file that is including it, therefore
defining itself again, but using \verb|#define| guards to change its definition.
For example, if file "X" includes \verb|define_trace.h|, then it will include
itself, "X", which will include \verb|define_trace.h| another time, and so on;
this cycle may repeat multiple times, until some condition is met. The reason is
to redefine the \verb|DECLARE_TRACE| macro in different ways to generate
different code. This is also used in other parts of the kernel, namely "event
tracing" which will be explained later in this section.

Finally the developers can use the \verb|trace_sched_entry()| trigger the
tracepoint. The callstack looks like this:

\begin{verbatim}
trace_sched_entry(...)
  __do_trace_sched_entry(...)
      static_call(tp_func_sched_entry)
\end{verbatim}

A \textit{static call} is a mechanism that uses code patching to replace global
function pointers. It allows directs calls to be used instead of indirect calls.
In this particular case, instead of having a pointer to the callback function
stored somewhere in the tracepoint structure which needs to be loaded from
memory, a call to its address is directly patched where the \verb|static_call|
call lives therefore removing one layer of indirection. There may be multiple
callbacks registered, in this case the call will be patched to an iterator which
simply loops over all registered callbacks and calls them.

Before calling the \verb|static_call|, a check is made to determine if the
tracepoint is active or not by checking if the callback address is present. To
avoid a conditional branch instruction in the if statement, the code is patched
at runtime via a mechanism called \verb|static_key| that replaces the if
statement with a jump or a NOP instruction depending on whether the event is
active or not. Note that this is different than \verb|static_call| because it
replaces a conditional branch (compare + jump instructions) and not a function
call. This decreases the runtime performance impact of a disabled tracepoint, as
the only effective penalty is overall increased code section size due to the
tracepoint generated functions.

\subsubsection*{Event Tracing}

A tracepoint provides an object which calls a callback function when triggered.
Additional work is necessary to make this system interact with the rest of the
tracing frameworks in the kernel such as ftrace and perf. To simplify this, the
macro \verb|TRACE_EVENT| should be used instead of \verb|DEFINE_TRACE|. Creating
a tracepoint using this macro is referred to as "event tracing", which is not to
be confused with "perf events tracing".

The \verb|DEFINE_TRACE| macro is responsible for creating a proper tracepoint
that can be used in the kernel code, creating a callback that can be hooked to
said tracepoint which must record the formatted data into the tracer ring
buffer. To accomplish this, the \verb|TRACE_EVENT| macro is broken into six
components, which correspond to the parameters of the macro:

\begin{itemize}
  \item \textit{name}: the name of the tracepoint to be created

  \item \textit{prototype}: the prototype for the tracepoint callbacks

  \item \textit{args}: the arguments that match the prototype

  \item \textit{struct}: the structure that a tracer could use (but is not
  required to) to store the data passed into the tracepoint

  \item \textit{assign}: code written in C to assign the data to the structure.

  \item \textit{print}: code written in C to output the structure in human
  readable ASCII format.

\end{itemize}

For example, consider the trace event in
\textit{\$LINUX/fs/fuse/fuse\_trace.h:126}:

\begin{Verbatim}[numbers=left, numbersep=5pt, frame=single]
TRACE_EVENT(fuse_request_end,
  TP_PROTO(const struct fuse_req *req),

  TP_ARGS(req),

  TP_STRUCT__entry(
    __field(dev_t,    connection)
    __field(uint64_t,  unique)
    __field(uint32_t,  len)
    __field(int32_t,  error)
  ),

  TP_fast_assign(
    __entry->connection  =  req->chan->conn->dev;
    __entry->unique    =  req->in.h.unique;
    __entry->len    =  req->out.h.len;
    __entry->error    =  req->out.h.error;
  ),

  TP_printk("connection %u req %llu len %u error %d", __entry->connection,
      __entry->unique, __entry->len, __entry->error)
);
\end{Verbatim}

This code creates the trace event \verb|trace_fuse_request_end| using the
specified parameters to format the event to the ring buffer. The expansion of
this macro uses the same trick as \verb|DEFINE_TRACE| by redefining itself a
total of 7 times which will not be covered here due to the high complexity of
the expansion.

Since \verb|TRACE_EVENT| generates a lot of code and increases the size of the
kernel binary, the macro \verb|DECLARE_EVENT_CLASS| and \verb|DEFINE_EVENT|
should be used for tracepoints that share some code.

\subsubsection*{Syscall Tracepoints}

For various use cases, it may be useful for the user to trace accesses to
systemcalls. For this reason, special tracepoints are placed specifically for
systemcalls which are triggered when the function is entered and exited.

A system call is defined by the \verb|SYSCALL_DEFINEX| family of macros. For
example, the \verb|fork| systemcall as implemented in
\textit{\$LINUX/kernel/fork.c:2925} is defined with the following code:

\begin{Verbatim}[numbers=left, numbersep=5pt, frame=single]
#ifdef __ARCH_WANT_SYS_FORK
SYSCALL_DEFINE0(fork)
{
#ifdef CONFIG_MMU
  struct kernel_clone_args args = {
    .exit_signal = SIGCHLD,
  };

  return kernel_clone(&args);
#else
  /* can not support in nommu mode */
  return -EINVAL;
#endif
}
#endif
\end{Verbatim}

To support systemcall tracing, the \verb|SYSCALL_DEFINE0| macro expands to the
following code for x86, extracted from
\textit{\$LINUX/arch/x86/include/asm/syscall\_wrapper.h:244}:

\begin{Verbatim}[numbers=left, numbersep=5pt, frame=single]
#define SYSCALL_DEFINE0(sname)            \
  SYSCALL_METADATA(_##sname, 0);          \
  static long __do_sys_##sname(const struct pt_regs *__unused);  \
  __X64_SYS_STUB0(sname)            \
  __IA32_SYS_STUB0(sname)            \
  static long __do_sys_##sname(const struct pt_regs *__unused)
\end{Verbatim}

Notice on line 2 the macro \verb|SYSCALL_METADATA|, which expands to
the following code extracted from \textit{\$LINUX/include/linux/syscalls.h:178}:

\begin{Verbatim}[numbers=left, numbersep=5pt, frame=single]
#define SYSCALL_METADATA(sname, nb, ...)      \
  static const char *types_##sname[] = {      \
    __MAP(nb,__SC_STR_TDECL,__VA_ARGS__)    \
  };              \
  static const char *args_##sname[] = {      \
    __MAP(nb,__SC_STR_ADECL,__VA_ARGS__)    \
  };              \
  SYSCALL_TRACE_ENTER_EVENT(sname);      \
  SYSCALL_TRACE_EXIT_EVENT(sname);      \
  static struct syscall_metadata __used      \
    __syscall_meta_##sname = {        \
    .name     = "sys"#sname,      \
    .syscall_nr  = -1,  /* Filled in at boot */  \
    .nb_args   = nb,        \
    .types    = nb ? types_##sname : NULL,  \
    .args    = nb ? args_##sname : NULL,  \
    .enter_event  = &event_enter_##sname,    \
    .exit_event  = &event_exit_##sname,    \
    .enter_fields  = LIST_HEAD_INIT(__syscall_meta_##sname.enter_fields), \
  };              \
  static struct syscall_metadata __used      \
    __section("__syscalls_metadata")      \
   *__p_syscall_meta_##sname = &__syscall_meta_##sname;
\end{Verbatim}

On line 8 and 9 the macros \verb|SYSCALL_TRACE_ENTER_EVENT| and
\verb|SYSCALL_TRACE_EXIT_EVENT| are responsible for creating the tracepoint, and
on line 10 a \verb|struct syscall_metadata| is created which is used to save
some information about the syscall and its arguments. Finally on line 21 a
pointer to the metadata struct is created in the section
\verb|__syscalls_metadata| which contains all metadata from all systemcalls.

Whenever a systemcall is executed by the user, the following functions are
called from top to bottom:

\begin{verbatim}
entry_SYSCALL_64
   do_syscall_64
      syscall_enter_from_user_mode
         syscall_trace_enter
            trace_syscall_enter
              trace_sys_enter
\end{verbatim}

The last function, \verb|trace_sys_enter|, is a trace event defined in
\textit{\$LINUX/include/trace/events/syscalls.h}:

\begin{Verbatim}[numbers=left, numbersep=5pt, frame=single]
TRACE_EVENT_SYSCALL(sys_enter,

  TP_PROTO(struct pt_regs *regs, long id),

  TP_ARGS(regs, id),

  TP_STRUCT__entry(
    __field(  long,    id    )
    __array(  unsigned long,  args,  6  )
  ),

  TP_fast_assign(
    __entry->id  = id;
    syscall_get_arguments(current, regs, __entry->args);
  ),

  TP_printk("NR %ld (%lx, %lx, %lx, %lx, %lx, %lx)",
      __entry->id,
      __entry->args[0], __entry->args[1], __entry->args[2],
      __entry->args[3], __entry->args[4], __entry->args[5]),

  syscall_regfunc, syscall_unregfunc
);
\end{Verbatim}

This last trace event creates the actual tracepoint that logs all systemcalls,
using the metadata registered from \verb|SYSCALL_DEFINEX| for printing.

\subsection{Dynamic Events}

\subsubsection*{Kprobes and Kretprobes}

\textit{Kprobes} are events that can be dynamically placed almost anywhere on
the kernel. They use code patching to replace any instruction with a call to a
trace function, which saves and values of the registers and restores them when
it completes. The instruction that was replaced will be single-stepped
(executed) by the kprobe, so the program will continue to run as originally
expected. Such instrumentation does not require any special infrastructure on
the traced function, which makes kprobes particularly useful and versatile. The
kprobe infrastructure is available with the kernel compile option
\verb|CONFIG_KPROBES|.

Two different kinds of probes exist: \textit{kprobes} which are often placed at
the beginning of functions, and \textit{kretprobes} which are called at the end
of the function and may alter the return value. A kprobe or kretprobe sets up a
call to two functions, if specified: a \textit{pre-handler}, which is called
before single-stepping the replaced instruction, and a \textit{post-handler}
which is instead executed after.

A kprobe is represented by the type \verb|struct kprobe| which is reported
below, with comments explaining the various members:

\begin{verbatim}
typedef int (*kprobe_pre_handler_t) (struct kprobe *, struct pt_regs *);
typedef void (*kprobe_post_handler_t) (struct kprobe *, struct pt_regs *,
              unsigned long flags);

struct kprobe {
  struct hlist_node hlist;
  /* list of kprobes for multi-handler support */
  struct list_head list;
  /*count the number of times this probe was temporarily disarmed */
  unsigned long nmissed;
  /* location of the probe point */
  kprobe_opcode_t *addr;
  /* Allow user to indicate symbol name of the probe point */
  const char *symbol_name;
  /* Offset into the symbol */
  unsigned int offset;
  /* Called before addr is executed. */
  kprobe_pre_handler_t pre_handler;
  /* Called after addr is executed, unless... */
  kprobe_post_handler_t post_handler;
  /* Saved opcode (which has been replaced with breakpoint) */
  kprobe_opcode_t opcode;
  /* copy of the original instruction */
  struct arch_specific_insn ainsn;
  /*
   * Indicates various status flags.
   * Protected by kprobe_mutex after this kprobe is registered.
   */
  u32 flags;
};
\end{verbatim}

A kprobe can be registered and unregistered with the functions
\verb|register_kprobe()| and \verb|unregister_kprobe()|. They can be temporarely
enabled with \verb|enable_kprobe()| and disabled with \verb|disable_kprobe()|.
The list of registered kprobes is accessible by reading the file
\textit{\$DEBUGFS/kprobes/list} where \verb|$DEBUGFS| is the location where the
\textit{debugfs} filesystem is mounted.

Let's look at an example kernel module that register a kprobe on the
\verb|do_sys_openat2| function which is called by the \verb|openat2| systemcall,
and logs the name of the file that the user wants to open:

\begin{Verbatim}[numbers=left, numbersep=5pt, frame=single]
#include <linux/module.h>
#include <linux/kprobes.h>

#define MAX_FILENAME_LEN 1024

/* This gets executed before single-stepping the probed instruction */
static int hello_kprobe_pre_handler(struct kprobe *p, struct pt_regs *regs)
{
  const char __user * user_filename =
    (const char __user*) regs_get_kernel_argument(regs, 1); /* regs start at 0 */
  if (!user_filename) {
    printk(KERN_ERR "Kprobe: error reading filename in pre handler\n");
    return -1;
  }

  char filename[MAX_FILENAME_LEN] = {0};
  long ret = raw_copy_from_user(filename, user_filename,
                                MAX_FILENAME_LEN);
  if (ret < 0) {
    printk(KERN_ERR "Kprobe: error copying filename\n");
    return -1;
  }

  printk(KERN_INFO "Kprobe: intercepted access to %s\n", filename);

  return 0;
}

/* This gets executed after single-stepping the probed instruction */
static void hello_kprobe_post_handler(struct kprobe *kprobe,
                                      struct pt_regs *regs,
                                      unsigned long flags)
{
  /* does nothing */
}

struct kprobe kp = (struct kprobe) {
  .symbol_name  = "do_sys_openat2",
  .pre_handler  = hello_kprobe_pre_handler,
  .post_handler = hello_kprobe_post_handler,
};

static int __init hello_kprobe_init(void)
{
  printk(KERN_INFO "Kprobe: Hello, kprobe!\n");

  int ret = register_kprobe(&kp);
  if (ret < 0) {
    printk(KERN_ERR "Kprobe: error registering kprobe\n");
    return -1;
  }
  return 0;
}

static void __exit hello_kprobe_cleanup(void)
{
  unregister_kprobe(&kp);
  printk(KERN_INFO "Kprobe: unregistered");
}

module_init(hello_kprobe_init);
module_exit(hello_kprobe_cleanup);

MODULE_AUTHOR("Giovanni Santini");
MODULE_DESCRIPTION("kprobe example");
MODULE_LICENSE("GPL v2");
\end{Verbatim}

On line 7 and line 30 the kprobe's pre-handler \verb|hello_kprobe_pre_handler()|
and post-handler \verb|hello_kprobe_post_handler()| functions are defined. Both
pre and post handlers can access the CPU registers via the struct \verb|struct pt_regs|.
Looking now at the pre-handler, the values of the registers correspond to the
argument to the function according to the C ABI for the specific CPU
architecture used, since the kprobe was placed in a function. The pre-handler
gets the second argument from the function using
\verb|regs_get_kernel_argument()| on line 9, which corresponds to the filenane,
then copies its value from userspace to kernelspace on line 17 and logs it on
line 24 using \verb|printk()| which writes it to a special ringbuffer used for
kernel prints which is accessible from \textit{\$PROCFS/kmsg}. On line 37 the
code defines the kprobe \verb|kp| with its pre and post handler, and the
location where it should be placed. The specific address of the kprobe will be
resolved from the symbol specified in the \verb|symbol_name| member, which will
use the \verb|System.map| symbol table infrastructure containing the positions
of all the symbols in the kernel. Finally on line 47 the kprobe is registered
when the module is loaded, and unregistered in line 57 when the module is
unloaded.
